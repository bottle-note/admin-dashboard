# 위스키 Excel 벌크 등록 Spec

## Summary

운영자가 위스키 Excel 양식을 내려받고, 작성한 파일의 오류와 중복 가능성을 확인한 뒤 오류가 없는 행을 한 번에 등록한다.

## Operator Goal

- 빈 Excel 양식을 내려받아 위스키 정보를 작성한다.
- 작성한 파일을 업로드해 어느 행을 고쳐야 하는지 확인한다.
- 수입 신고 화면에서 만든 등록 초안도 같은 양식에 값을 채운 뒤 이 화면에서 검증한다.

## Domain Model

- **양식**: 서버가 제공하는 고정 XLSX다. 시트, 헤더, 설명 행을 유지해야 한다.
- **검증**: 저장 없이 파일 구조와 각 행의 필수값·참조 ID·중복을 검사한다.
- **오류**: 해당 행은 등록할 수 없다. 예: 필수값 누락, 잘못된 지역·증류소·카테고리 ID, 파일 내부 중복.
- **경고**: 이미 등록된 위스키와 강하게 일치하는 후보가 있는 등 운영자 확인이 필요한 상태다.
- **정규화 행**: Excel 검증을 통과한 값을 서버가 저장 가능한 JSON 형태로 정리한 결과다.
- **일괄 등록**: 모든 행을 다시 검증한 뒤 하나의 트랜잭션으로 저장한다. 한 행이라도 오류가 있으면 0건 저장한다.

## API Contract

| 기능          | API                                                                | 현재 역할                                                          |
| ------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 양식 다운로드 | `GET /v1/alcohols/excel/template`                                  | XLSX 바이너리를 반환한다.                                          |
| 파일 검증     | `POST /v1/alcohols/excel/validate` (`multipart/form-data`, `file`) | 저장 없이 검증 결과와 행별 `clientRowId`, `normalized`를 반환한다. |
| JSON 검증     | `POST /v1/alcohols/bulk/validate`                                  | 최대 1,000행을 저장 없이 검증한다.                                 |
| 일괄 등록     | `POST /v1/alcohols/bulk`                                           | 전체 행을 재검증하고 오류가 없으면 모두 저장한다.                  |

검증 응답은 `totalRows`, `validRows`, `invalidRows`, `warningRows`와 행별 `rowNumber`, 이름·규격 정보, `errors`, `warnings`, 중복 후보 ID, 정규화 행을 제공한다. 검증 API는 빈 파일도 정상적으로 0건 결과로 반환할 수 있다.

등록 성공 응답은 `createdRows`, `rows(clientRowId, alcoholId)`, `validation`을 반환한다. 등록 직전 재검증이 실패하면 HTTP 400의 `errors`에 JSON 검증 결과와 같은 구조를 반환한다. 이때 화면은 `clientRowId`로 원래 Excel 행과 합쳐 기존 검증 결과 UI를 다시 사용한다. 반복 POST는 별도 등록이므로 자동 재시도하지 않는다.

## Screen Requirements

- 위스키 정보 관리 메뉴 아래에 `위스키 Excel 벌크 등록`을 추가한다. 기존 위스키 관리 화면과 같이 `ROOT_ADMIN`만 접근한다.
- 상단에는 `양식 다운로드`와 짧은 작성 안내를 둔다.
- 이어서 `.xlsx` 파일 선택 또는 드래그 영역과 `검증하기` 버튼을 둔다. 파일을 바꾸면 이전 검증 결과는 지운다.
- 검증이 끝나면 전체 행 / 오류 없는 행 / 오류 행 / 경고 포함 행을 요약으로 보여준다.
- 전체 행을 기본으로 표에 보여주며, 행 번호, 위스키명, 상태·확인 사항, compact 이미지 편집을 표시한다. 전체·오류·경고·이미지 미첨부 필터는 URL의 `issue` 파라미터로 관리한다.
- 오류가 없는 경우에도 “검증만 완료되었으며 아직 등록되지 않았습니다”를 표시한다.
- 테이블 아래 4단계 최종 전송 영역에서 등록·이미지 첨부·경고 건수를 확인한다. 오류가 없고 모든 행에 `normalized`가 있으며 이미지 업로드 중·실패 상태가 없을 때만 전송할 수 있다.
- 업로드 전에 등록 건수와 경고 건수를 확인하고, 반복 업로드 시 중복 등록될 수 있음을 알린다.
- 업로드 성공 후 등록 건수를 보여주고 같은 검증 결과의 업로드 버튼을 비활성화한다.
- 업로드 직전 서버 재검증이 실패하면 기존 Excel 행 정보에 새 오류·경고를 합쳐 검증 결과 표에 표시한다.

| 상태               | 화면 처리                                                            |
| ------------------ | -------------------------------------------------------------------- |
| 초기               | 양식 다운로드와 파일 선택만 노출                                     |
| 파일 선택          | 파일명·크기와 검증 버튼 노출                                         |

| 검증 완료          | 요약 및 전체 행·이미지 편집 표 노출                                  |
| 검증 오류          | 서버 메시지와 재시도·다른 파일 선택 제공                             |
| 0행 파일           | 0건 검증 결과와 작성 안내 노출                                       |
| 업로드 가능        | 오류 0건, 1행 이상, 모든 행에 정규화 값이 있을 때 업로드 버튼 활성화 |
| 업로드 재검증 실패 | 서버의 행별 결과를 기존 검증 결과 표에 반영하고 업로드 비활성화      |
| 업로드 완료        | 등록 건수 표시, 같은 파일의 중복 업로드 방지                         |

## Acceptance Criteria

- [ ] ROOT_ADMIN이 위스키 정보 관리 메뉴에서 벌크 등록 화면으로 이동할 수 있다.
- [ ] 운영자가 서버 제공 양식을 다운로드할 수 있다.
- [ ] 운영자가 `.xlsx` 파일을 업로드해 실제 검증 API 결과를 확인할 수 있다.
- [ ] 오류·경고 행의 행 번호와 수정 사유를 확인할 수 있다.
- [ ] 화면 어디에서도 검증만으로 등록되었다고 오해하지 않는다.
- [ ] 오류가 없는 검증 결과를 확인 후 한 번에 등록할 수 있다.
- [ ] 경고만 있는 행은 확인 후 등록할 수 있다.
- [ ] 등록 재검증 실패 시 한 건도 저장되지 않고 같은 결과 표에서 오류를 확인할 수 있다.
- [ ] 등록 성공 후 같은 검증 결과를 다시 업로드할 수 없다.

## 이미지 첨부 확장 — 2026-09-11

사용자가 승인한 와이어프레임의 네 단계(양식 다운로드 → 엑셀 업로드 → 검증 및 이미지 추가 → 최종 전송)를 기존 `/whisky/excel-bulk` 화면에 구현한다. 신규 일괄 등록 동작이며 기존 위스키 수정 API는 사용하지 않는다.

### API와 데이터 흐름

- 최신 공개 `https://bottle-note.github.io/workspace/openapi.admin.json`을 다시 조회했다.
- `POST /v1/alcohols/bulk`는 이미지 선택 항목에 기존 업로드의 `viewUrl`을 받는다고 명시한다.
- `GET /v1/s3/presign-url`의 `data.imageUploadInfo[]`에서 `uploadUrl`과 `viewUrl`을 받는다. 기존 S3 서비스가 `uploadUrl`로 PUT을 완료한 뒤 `viewUrl`을 반환한다. 저장 요청에 presigned 업로드 URL을 넣지 않는다.
- 최신 백엔드 main의 `AdminAlcoholBulkRowRequest.imageUrl`은 String이며, `DefaultAdminAlcoholBulkService`는 선택 필드로 정규화하고 값이 있으면 http/https URL인지 검사한다. 저장 시 `Alcohol.imageUrl`에 전달하고 이미지 리소스 활성화 이벤트를 발행한다.
- 기존 `AlcoholBulkRowRequest.imageUrl?: string | null`과 서비스 계약을 재사용한다. 새 API나 타입 완화는 추가하지 않았다.
- `useBulkAlcoholImages`가 `clientRowId`별 첨부 상태를 관리한다. 컴포넌트는 이 훅을 통해 업로드하고 서비스는 기존 `s3Service`를 사용한다.
- 최종 요청은 현재 `normalized`에 행별 완료 URL을 합쳐 생성한다. bulk 재검증 실패로 `normalized`가 null로 바뀌더라도 첨부 상태는 유지한다.

### 개별 이미지 편집

- `MediaUpload`의 `variant="compact"`는 56px `object-contain` 썸네일과 추가·변경·제거 버튼을 제공한다. 기본 variant의 기존 표현은 유지한다.
- 개별 파일 선택 시 기존 이미지 크롭과 WebP 전처리를 사용한다.
- 교체가 성공할 때까지 기존 URL을 유지한다. 실패한 파일은 재시도하거나 첨부 취소할 수 있다. 첨부 취소는 기존 URL을 유지하고, 제거는 URL을 비운다.
- 이미지 업로드·엑셀 검증·최종 전송 중에는 충돌하는 편집을 비활성화한다. 등록 완료 결과도 편집할 수 없다.
- 엑셀 오류로 정규화 값이 없는 행에는 오류 수정 후 첨부하도록 안내한다.

### 여러 이미지 추가

- 파일명 준비 → 이미지 선택 → 매칭 결과 확인을 다이얼로그에서 제공한다. 파일명 목록은 높이를 제한하지 않고, 제목부터 하단 버튼까지 모달 전체를 하나의 스크롤 영역으로 사용한다.
- 권장 파일명은 `엑셀 행 번호(최소 3자리)_한글 이름`이다. 한글 이름이 없으면 영문 이름을 사용한다. 이름은 NFC 정규화, 공백·파일명 금지 문자 치환, 길이 제한을 적용한다.
- 복사 버튼은 확장자를 제외한 이름을 복사한다. 사용자는 파일명을 변경하고 기존 확장자를 유지한다. Excel 양식 변경은 없다.
- 매칭은 선택 파일의 확장자를 제외하고 NFC 정규화한 이름과 권장 파일명의 정확한 일치만 사용한다. 동명 위스키는 행 번호로 구분한다.
- 대상 없는 파일·지원하지 않는 형식·같은 행에 연결되는 중복 파일은 제외한다. 파일 목록에서 중복 파일 하나를 제거하면 남은 파일을 업로드할 수 있다.
- 기존 이미지가 있으면 `기존 이미지 교체`를 선택한 파일만 업로드한다.
- 파일 미리보기, 연결 대상, 매칭·업로드 상태를 표시한다. 여러 파일은 원본 비율을 유지하며 기존 정책(WebP 품질 70, 긴 변 최대 1600px)으로 전처리하고 최대 3개씩 업로드한다.
- 성공 파일을 보존하고 실패 파일만 재시도한다. 다이얼로그를 닫아도 실패 상태는 행에 남고 해결 전 최종 전송을 막는다.

### 초기화와 전송

- 이미지 없이 등록할 수 있다. 첨부한 파일의 업로드 진행·실패는 해결해야 한다.
- 엑셀 교체·재검증은 첨부 연결을 초기화한다. 첨부가 있으면 초기화 안내와 취소 선택을 제공한다.
- 업로드 세션 번호로 오래된 비동기 결과가 새 검증 결과에 반영되는 것을 막는다.
- S3 업로드 자체와 위스키 등록은 별개다. 최종 등록을 취소해도 이미 업로드된 파일의 삭제 API는 호출하지 않는다.

### 검증 기록

- `pnpm build`: 타입 검사 및 프로덕션 빌드 통과(기존 번들 크기·Browserslist 경고).
- `pnpm lint`: 오류 없음, 기존 경고 7개.
- 기존 벌크 E2E의 버튼·섹션 이름을 새 화면에 맞췄다.
- 실제 양식 다운로드·Excel 검증·개별 크롭·S3 업로드·다중 매칭·부분 실패 재시도·최종 imageUrl 전달을 확인하는 E2E를 추가했다. 재현이 어려운 presign 실패 1회와 최종 등록만 interception한다.
- 최초 E2E 실행은 테스트 계정 설정 부재로 중단되었다. 프로젝트의 기존 dev 환경 동기화 후 계정은 로드됐지만 실제 로그인에서 `접근 권한이 없습니다` 응답으로 setup이 실패했다. 실제 업무 데이터의 등록은 실행하지 않았다.
- Chrome에서도 개발 환경 로그인 거절을 확인했다. 검증 테이블·다이얼로그의 실제 화면 및 실제 S3 응답 확인은 유효한 관리자 로그인 확보 후 필요하다.

- 후속 스크롤 수정: 로그인된 localhost:5173의 실제 89행 모달에서 내부 스크롤 영역이 0개임을 확인했다. 모달 전체를 아래로 스크롤해 이미지 선택·매칭 결과·하단 버튼의 정상 노출을 확인했고 lint/build가 통과했다. 이미지 업로드 E2E 검증과는 별개다.


### 기존 이미지 크롭 편집 — 2026-09-12

- compact의 `수정` 및 썸네일 클릭은 현재 이미지로 `ImageCropDialog`를 연다. `교체`는 새 파일 선택, `제거`는 첨부 해제다.
- `이미지 저장`은 기존 크롭·WebP 전처리 결과를 업로드하고 성공한 `viewUrl`로 해당 행을 교체한다. 취소는 기존 이미지를 보존하고 업로드 실패 시 행의 재시도·첨부 취소를 사용할 수 있다.
- 업로드 성공 시 `editFile`을 완료 URL과 함께 보관한다. 실패한 교체 파일(`file`)과 분리해 원래 이미지를 다시 편집할 수 있다. 다중 업로드 이미지도 같은 방식으로 재편집한다.
- 로컬 파일이 없는 기존 URL은 인증 헤더 없이 CDN에서 읽기를 시도한다. 2026-09-12 개발 CloudFront 이미지 GET 응답은 200과 `image/webp`지만 `Access-Control-Allow-Origin`이 없어 브라우저 재다운로드가 차단됨을 확인했다. 이 경우 파일 재선택 안내를 표시하며 URL은 보존한다. 새로 업로드한 파일의 재편집은 로컬 파일을 사용해 이 제한을 피한다. 기존 URL만 있는 이미지 편집에는 CDN의 허용 Origin 설정 보완이 필요하다.
- 실제 양식·검증·S3 업로드를 사용하는 Playwright 5개가 통과했다. 개별 첨부 → 수정 열기 → 취소 시 URL 보존 → 1:1 크롭 저장 → 새 URL 반영, 다중 업로드 이미지 재편집을 기존 도메인 흐름에 추가했다.
- 현재 계약의 bulk `imageUrl`은 선택 항목이며 업로드의 viewUrl을 사용한다. 기존 계약과 타입은 변경하지 않았다.

### 작업 자동화 접근성 — 2026-09-12

- `/llms.txt`와 `/agent-guides/whisky-excel-bulk.md`에 화면 경로, 신규 등록 의미, 행 식별, 매칭 규칙, 크롭 좌표 단위, 오류 복구 및 재전송 주의사항을 문서화했다. HTML에서 `rel="describedby"`로 안내 문서를 연결한다. 정적 가이드에는 현재 작업 데이터나 인증 정보를 포함하지 않는다.
